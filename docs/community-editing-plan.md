# 百科式开放编辑 · 设计方案（待评审）

> 状态：**已实施** —— 下面的设计稿保留原文；P1 ~ P4 都已上线，实现差异与后续改动见文末
> 「实施记录（2026-09-24）」「攒批写回（2026-10-05）」。
> 结论先行：**能做，Cloudflare 完全够用，但"真·百科"（改完立刻可见）会推翻现有静态架构 —— 推荐做「开放投稿 + 审核后进 git」。**

---

## 0. 一页结论

| 问题 | 答案 |
|---|---|
| 需要数据库吗？ | **需要**，用 Cloudflare **D1**（SQLite）。免费额度 500 万行读/天、10 万行写/天、5 GB 存储 |
| 需要后端吗？ | **需要**，一个 Worker 脚本（现在这个 Worker 是纯静态资源，一行脚本都没有） |
| 站点会变成动态的吗？ | **不会。** 官方路由规则：有静态资源 + Worker 脚本时，**静态资源优先命中，匹配不到才调用 Worker**。808 个页面照旧由边缘直接发出，性能不变 |
| 编辑能立刻生效吗？ | **不能，也不需要。** 写回 git → 触发重建 → 约 1~2 分钟上线。这是为了保住静态架构与可回滚性（2026-10-05 起改为**攒批**：审核通过只是排队，站长点一次「写回仓库」才发布，见文末「攒批写回」） |
| 审核后台要自己写登录吗？ | **不用。** 用 **Cloudflare Access 按路径保护** `/admin`，GitHub/邮箱登录，零登录代码 |
| 工作量 | 分 4 期，累计约 **3~5 天**专注开发；之后**每天都得有人看一次审核队列** |

**最重要的前提**：这套东西解决的是"投稿门槛高"，**不解决"没人管"**。开放而没有管理员，几天就会被灌满。评审时请先回答第 15 节第 1 问：**谁来做审核员。**

## 1. 目标与非目标

### 目标

1. 任何人**不需要懂 git、不需要 GitHub 账号**，就能对某张地图提交资料修正。
2. 所有改动**经审核后才发布**，发布路径仍是 git 提交 —— 可追溯、可回滚、能被 CI 拦住。
3. 站点保持**纯静态**，不牺牲已经做过的性能优化。
4. 审核工作量**轻**：一屏看一条、一键通过/驳回。

### 明确不做（非目标）

| 不做 | 原因 |
|---|---|
| ❌ 编辑立即生效（真 wiki） | 要运行时渲染 808 个页面，静态架构、缓存头、`_headers` 规则、Pagefind 搜索全部要重做 |
| ❌ 开放编辑 `src/content/maps/*.mdx` 正文 | 447 个自动生成条目带 `generated by` 标记，`npm run maps:generate` 会覆盖它们 |
| ❌ 用户上传任意文件（图片/附件） | 风险最高的一类功能，留到第 4 期且必须走 KV + 审核 + 体积限制 |
| ❌ 自建账号体系（注册/密码/找回） | 用 Cloudflare Access 顶替，零代码 |
| ❌ 现在就迁移现有 547 个条目 | 社区内容独立存放（见第 3 节），不碰存量数据 |

## 2. 架构

```
                    ┌─────────────────────────────────────────┐
   读者/贡献者 ──────▶│  ze-map.cn  （Cloudflare Worker）        │
                    │                                          │
                    │  /maps/… /preview/… /entity/…            │
                    │  ↓ 静态资源优先命中（不经过 Worker 代码）  │
                    │  dist/  ← 构建产物                        │
                    │                                          │
                    │  /api/submit  /api/vote   ← Worker 接管   │
                    └───────────────┬──────────────────────────┘
                                    │
                             ┌──────▼──────┐
                             │  D1（SQLite）│  投稿队列 / 投票 / 限流
                             └──────┬──────┘
                                    │
   站长 ──▶ /admin（Cloudflare Access 保护）── 审核
                                    │
                                    │ 通过
                             ┌──────▼──────────────────────┐
                             │ GitHub API：写入             │
                             │ data/community/<slug>.json   │
                             └──────┬──────────────────────┘
                                    │ commit → push
                             ┌──────▼──────────────────────┐
                             │ Cloudflare Workers Builds    │
                             │ npm run build → wrangler deploy │
                             └──────────────────────────────┘
```

**关键性质**

- **静态优先**：`assets` 存在时，命中静态文件的请求**不会执行 Worker 脚本**。所以加脚本不会让现有页面变慢，也不会因为 Worker 报错而挂站 —— 最坏情况只是 `/api/*` 返回 500。
- **git 仍是唯一真相**：D1 只存"还没进仓库的东西"，随时可以清库重来而不丢内容。
- **可回退**：删掉 `main` 与 `d1_databases` 两行配置，Worker 就退回纯静态资源模式。

## 3. 内容放哪：三层模型

| 层 | 位置 | 谁写 | 会不会被覆盖 |
|---|---|---|---|
| ① 自动生成 | `src/content/maps/*.mdx`（带 `generated by` 标记） | `npm run maps:generate` | ⚠️ 会被覆盖 |
| ② 人工资料 | `data/research/<map>.json` | 检索/手写 | ❌ 不会（人工成果） |
| ③ **社区投稿（新增）** | **`data/community/<map>.json`** | **Worker 审核通过后写入** | ✅ **永不覆盖** |

**新增第 ③ 层是这套方案的地基。** 它带来的好处：

- 社区改动**永远不碰生成物**，不存在"被 `maps:generate` 冲掉"的问题；
- 一张图一个文件，diff 极小，一眼能看出谁改了什么；
- 出问题就删这一个文件，等价于回滚；
- 构建时读取，用 `import.meta.glob()` 由打包器解析（**不用相对路径 `fs.readFile`** —— 这正是当初 `/bundle` 构建失败的根因，绝不能重犯）。

数据形状（示意）：

```jsonc
// data/community/ze_flowering.json
{
  "updatedAt": "2026-09-24T06:00:00Z",
  "fields": {
    "difficulty": { "value": "普通", "by": "xianoom", "at": "…", "source": "工坊描述" },
    "tags":       { "value": ["传送门多", "风景", "多关卡"], "by": "…", "at": "…" }
  },
  "body": [
    { "id": 12, "text": "第二关的传送门……", "by": "…", "at": "…" }
  ]
}
```

渲染优先级：**③ 社区 > ② 人工 > ① 自动生成**（每一层都能被上一层覆盖，且页面上标注来源）。

## 4. 内容边界：哪些能改

| 字段 | 谁能改 | 校验 | 备注 |
|---|---|---|---|
| `difficulty` | 任何人**投票** | 必须命中枚举 `入门/简单/普通/困难/火星/入土/未知` | 聚合投票，不直接改字段。**今天那次构建失败就是填了枚举外的「普通」** |
| `tags` | 投稿（审核） | 只能是**受控词表**里的标签；新增标签需审核确认 | 从下拉多选，**从源头消灭「两个数组漏逗号」** |
| `author` / `authorNote` | 投稿（审核） | 字符串，≤120 字 | 易引发署名争议，必须带来源 |
| `version` / `players` / `duration` / `stages` | 投稿（审核） | `stages` 必须是整数 | |
| `videoUrls` / `sources` | 投稿（自动发布候选） | 必须是合法 URL，且域名白名单（bilibili / youtube / steam / bbs） | 第 4 期可放开自动发布 |
| 攻略 / 剧情 / 神器说明（正文） | 投稿（审核） | 纯 Markdown 子集（**禁 JSX**），≤4000 字 | 只落 `data/community`，不碰生成物 |
| 图片 | 第 4 期再说 | — | 需要 KV + 体积/格式限制 |

**正文只收纯 Markdown，不收 MDX/HTML。** 现有条目里已经踩过"工坊正文含 `<` 和 `{` 被当 JSX 解析导致构建失败"的坑，社区入口必须从格式上堵死。

## 5. D1 数据模型

```sql
-- 投稿队列（核心表）
CREATE TABLE submissions (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  map_slug    TEXT    NOT NULL,               -- ze_flowering
  field       TEXT    NOT NULL,               -- difficulty|tags|author|body|link|…
  value       TEXT    NOT NULL,               -- JSON 编码
  note        TEXT,                           -- 提交者的理由 / 来源
  submitter   TEXT,                           -- 昵称（选填）
  contact     TEXT,                           -- QQ / 邮箱（选填，便于追问）
  ip_hash     TEXT    NOT NULL,               -- sha256(ip + 盐)，不存明文 IP
  status      TEXT    NOT NULL DEFAULT 'pending',  -- pending|approved|rejected|applied
  created_at  INTEGER NOT NULL,
  reviewed_at INTEGER,
  reviewer    TEXT,                           -- 审核人（Access 身份）
  reject_note TEXT,
  commit_sha  TEXT                            -- 写回 git 后的提交号
);
CREATE INDEX idx_sub_status ON submissions(status, created_at);
CREATE INDEX idx_sub_map    ON submissions(map_slug, field);

-- 难度投票（一人一票，可改票）
CREATE TABLE difficulty_votes (
  map_slug   TEXT NOT NULL,
  value      TEXT NOT NULL,
  ip_hash    TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (map_slug, ip_hash)
);

-- 限流计数
CREATE TABLE rate_limits (
  ip_hash TEXT NOT NULL,
  window  TEXT NOT NULL,        -- '2026-09-24T05'（按小时）
  count   INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (ip_hash, window)
);

-- 黑名单（封禁滥用者）
CREATE TABLE bans (
  ip_hash  TEXT PRIMARY KEY,
  reason   TEXT,
  banned_at INTEGER NOT NULL
);
```

> 注意**不存明文 IP**，只存加盐哈希 —— 既够用来限流/封禁，又不构成个人信息收集。

## 6. API 设计

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| `POST` | `/api/vote` | 公开 + Turnstile | 难度投票 |
| `GET` | `/api/stats?map=<slug>` | 公开 | 投票分布（可缓存 60s） |
| `POST` | `/api/submit` | 公开 + Turnstile | 提交改动，进队列 |
| `GET` | `/api/admin/queue` | **Access 保护** | 待审列表 |
| `POST` | `/api/admin/review` | **Access 保护** | `{id, action: approve\|reject, rejectNote}` |
| `POST` | `/api/admin/ban` | **Access 保护** | 封禁 ip_hash |

约定：
- 全部返回 JSON；错误统一 `{ ok: false, error: "<人话>" }`；
- **服务端必须重新校验一遍 schema**（不能信前端）。枚举、长度、URL 白名单、标签词表都在 Worker 里做，并且**与 `src/content.config.ts` 共用同一份枚举定义**（抽成一个 `shared/schema.mjs`，构建期与 Worker 都引它，避免两边漂移）；
- Turnstile token 校验失败 → 400；限流命中 → 429。

## 7. 防滥用

| 手段 | 做法 |
|---|---|
| 人机验证 | **Cloudflare Turnstile**（免费），前端挂载 + 服务端 `siteverify` |
| 限流 | 按 `ip_hash` 计数：投票每小时 20 次；投稿每小时 300 次 + 每天 2000 次兜底（2026-09-28 由 5 次/小时放宽，见 `shared/submission-fields.mjs` 的 `LIMITS`）；超限 429 |
| 字段白名单 | 只接受第 4 节列出的字段，其余一律丢弃 |
| 长度上限 | 备注 ≤500 字、正文 ≤4000 字、昵称 ≤32 字 |
| 链接白名单 | 只允许 bilibili / youtube / steamcommunity / 已知论坛域名，防钓鱼与广告 |
| 内容过滤 | 关键词黑名单 + 同一 `ip_hash` 连续被驳回 3 次自动进入人工复核 |
| 封禁 | `bans` 表，一键封禁 |
| 不存明文 IP | 只存哈希 |

**这些只能挡机器人和顺手捣乱的人，挡不住有心人。** 审核才是真正的防线。

## 8. 审核工作流

```
读者提交 ──▶ D1 pending ──▶ /admin 队列 ──┬─ 通过 ──▶ 写 data/community/<slug>.json ──▶ 构建 ──▶ 上线
                                          └─ 驳回（填理由）──▶ 记录，可回看
```

- **认证：零代码。** 在 Cloudflare Zero Trust 里建一个 self-hosted Access 应用，把路径 `ze-map.cn/admin` 挂上策略（GitHub 或邮箱登录），其余路径保持公开。
  - ⚠️ **一个已知限制**：Worker 带静态资源时，内部路由**不会把 `ctx.access` 传给用户 Worker**（官方文档明确写了）。所以 Worker 里读不到 `ctx.access.getIdentity()`。两个应对，实施时实测取一：
    1. 读 Access 注入的 `Cf-Access-Jwt-Assertion` / `Cf-Access-Authenticated-User-Email` 请求头（Access 在边缘已校验，路径被保护即可信）；
    2. 审核 API 单独放一个**不带静态资源绑定**的 Worker，`ctx.access` 就可用。
- **审核台长什么样**：一屏一条卡片 —— 地图名 + 字段 + 现值 vs 新值 + 理由 + 来源链接 + 提交者 → 「通过 / 驳回」。键盘 `j/k/a/r` 操作。
- **审完不要立刻构建**：把一小时内的通过项**攒成一次提交**，避免频繁触发构建（每次构建约 1~2 分钟，且占部署次数）。
- **驳回理由要回显**给提交者（凭 `id` 查询）。

## 9. 写回 git 的实现

- 用一个**细粒度 PAT**（Fine-grained personal access token）：**只授权 `hhjjdsj/ze-map-site` 这一个仓库、只给 Contents: Read and write**，存成 Worker secret `GITHUB_TOKEN`。
- 写入用 `PUT /repos/{owner}/{repo}/contents/{path}`：
  - 新文件：不带 `sha` 直接创建；
  - 已有文件：先 `GET` 拿当前 `sha` 再带 `sha` 更新（**乐观并发**：拿到的 sha 过期会被 GitHub 拒绝，此时重新拉取并从 D1 里重放已通过的改动 —— 因为 D1 才是权威副本，这个冲突是可恢复的，不是数据丢失）。
  - ⚠️ **2026-10-05 起改为 Git Data API 一次提交多个文件**（blob → tree → commit → 移动 ref），理由见文末「攒批写回」一节；上面这条保留为最初的单文件实现记录。
- **提交信息写清来源**：`社区投稿：ze_flowering 难度 未知 → 普通（by 提交者昵称，审核 站长）`。这样 `git log` 本身就是内容变更史。
- 预期提交会触发 Cloudflare Workers Builds（**待实测确认**：API 创建的提交是否等同于 push 事件触发构建；若不触发，退路是改走 Cloudflare 的构建触发 API）。

## 10. `wrangler.jsonc` 的变化（预览，尚未应用）

```jsonc
{
  "name": "ze-map-site",
  "compatibility_date": "2026-09-23",
  "main": "worker/index.ts",                 // ① 新增：Worker 脚本入口（wrangler 原生支持 TS）
  "assets": {
    "directory": "./dist",
    "not_found_handling": "404-page",
    "html_handling": "auto-trailing-slash",
    "binding": "ASSETS",                     // ② 新增
    "run_worker_first": ["/api/*"]           // ③ 新增：只有 /api/* 先走 Worker，其余仍是静态优先
  },
  "d1_databases": [                          // ④ 新增
    { "binding": "DB", "database_name": "ze-map-community", "database_id": "<控制台生成>" }
  ],
  "vars": { "TURNSTILE_SITE_KEY": "<公开的 site key>" },
  "previews": {}
}
```

- Secrets（用 `npx wrangler secret put` 设置，不进仓库）：`GITHUB_TOKEN`、`TURNSTILE_SECRET`、`IP_SALT`。
- **构建与部署命令完全不变**：`npm run build` / `npx wrangler deploy`，Cloudflare 那边不用改。
- 到了这一步，你之前问的那个 **Worker Previews 才真正有用** —— 它是测试 `/api/*` 改动的安全区。
- 本地开发会分裂成两套：`npm run dev`（纯站点，无 Worker）与 `npx wrangler dev`（站点 + Worker + 本地 D1）。这是个真实的开发体验代价。

## 11. 分期实施计划

每一期都能**独立上线、独立回退**，不必一次做完。

| 期 | 内容 | 产出 | 预估 | 回退方式 |
|---|---|---|---|---|
| **P0** 准备 | 开启 Zero Trust、建 D1 库、生成细粒度 PAT、申请 Turnstile key | 控制台配置，无代码 | 0.5 天 | 删库删 key |
| **P1** 投票 | 只做难度/标签投票：`/api/vote` + `/api/stats` + 页面上一小块 UI | **读者立刻有参与感**，同时验证 Worker + D1 这条路 | 0.5~1 天 | 删 `main`/`d1` 两行配置 |
| **P2** 闭环 | 投稿表单 → D1 队列 → `/admin` 审核台（Access 保护）→ 写回 git → 构建时读取 `data/community/` 并显示 | **完整可用的百科式投稿** | 2~3 天 | 保留审核台手动关闭投稿入口 |
| **P3** 治理 | 贡献榜、逐条历史、diff 预览、回滚按钮、自动发布白名单字段（仅 URL 类） | 降低长期审核成本 | 1~2 天 | 逐项开关 |
| **P4** 可选 | 图片上传（Workers KV + 体积/格式限制 + 审核）—— 已实现（2026-09-25） | 补全资料形态 | 1~2 天 | 关入口 |

**建议：P1 先上，观察两周。** 如果连投票都没什么人参与，就不要做 P2 了 —— 那说明瓶颈不是"门槛高"，而是"没人愿意贡献"，做完整套也只是给自己添一个每天要看的后台。

## 12. 成本与限额（官方文档数据，2026-09-24 查）

| 资源 | 免费额度 | 够不够 |
|---|---|---|
| **D1 行读** | 500 万 / 天 | 远超需要 |
| **D1 行写** | **10 万 / 天** | 够（一次投稿 = 1~2 行） |
| **D1 存储** | 5 GB 总计 | 够（文本数据，几 MB 级） |
| Workers 请求 | 10 万 / 天 | 够（只走 `/api/*`，静态页不消耗） |
| Turnstile | 免费 | ✅ |
| Cloudflare Access | Zero Trust 需先开启，有免费额度（**具体人数上限以控制台为准**） | 审核员就你和 1~2 人 |
| KV | 读 10 万/天，**写仅 1000/天** | ⚠️ 写入太少，**不要用 KV 存投稿**（实际只拿它暂存待审封面图，一天几张的量，离上限很远） |

超限行为：D1 触及每日限额会**直接开始报错**（不是限速）。按你这规模不会碰到；真碰到就是被刷了，限流会先拦住。

## 13. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| **没人值守** | 队列堆积、垃圾内容 | P1 先验证参与度；审核台一屏一条；一键封禁 |
| Worker bug | 最坏 `/api/*` 500 | **静态优先**：站点本身不受影响，随时删配置回退 |
| GitHub token 泄露 | 有人能改仓库 | 细粒度 PAT、只限本仓库 contents:write；泄露就 revoke 重发 |
| 提交错误信息被发布 | 站点内容失真 | 审核制 + 必须填来源 + 页面标注贡献者与时间；git 可 revert |
| 并发写覆盖 | 丢了某条通过项 | D1 是权威副本，sha 冲突时重新拉取重放（见第 9 节） |
| 构建触发过频 | 消耗部署次数 | 攒批：一小时内合并成一次提交 |
| 版权争议 | 法律风险 | 只收事实性资料与链接，不收整段搬运的攻略；`NOTICE` 补社区内容条款 |
| 开发体验分裂 | 本地调试变复杂 | 文档写清两套 dev 命令 |

## 14. 治理：这部分无法用代码解决

1. **必须指定审核员。** 至少 1 人、最好 2~3 人（避免单点）。没有审核员的开放编辑一定烂掉。
2. **公开规则**：能提交什么、不能提交什么、多久审一次、什么情况封禁 —— 写在 `/contribute` 页面上。
3. **署名与版权**：社区贡献者要留名；地图本身版权归原作者（`NOTICE` 已写明），社区内容需要补一条许可说明（建议 CC BY-SA 或与代码一致的 MIT，由你定）。
4. **可追溯**：每笔改动都留下"谁提的、谁审的、依据什么、进了哪个 commit"。

## 实施记录（2026-09-24）

P1、P2 都已实现并通过测试。与上面设计稿有**三处偏离**，理由记在这里，免得以后看着文档纳闷：

1. **审核台认证改用密钥（`ADMIN_TOKEN`），没用 Cloudflare Access。**
   Access 要在控制台配 Zero Trust + Access 应用；而且官方文档明确写了「Worker 带静态资源时
   `ctx.access` 不会传给用户 Worker」，Worker 里读不到登录身份。密钥方案自包含、可端到端测试。
   以后想叠加 Access 作为第二层随时可以，不影响现有实现。

2. **社区内容在「读取层」合并，不在 content loader 里。**
   设计稿设想包一层 loader 再回写合并结果 —— **实测行不通**：glob 命中、store 能读能写、
   预演也显示「会合并 1 条」，但 `context.store.set()` 之后再 `get()` 回来仍是原值，
   渲染出的页面也没变。最终实现是 `src/lib/maps.ts` 的 `getMaps()`，所有页面统一从它取数。

3. **「写回 git」和「构建期读取并显示」拆成两步落地**，每步单独验证，没有一次做完。

实现期还发现两个坑，都已处理：

- `.gitignore` 里的 `data/*` 会连 `data/community/` 一起忽略，靠补一条 `!data/community/`
  白名单放行 —— 少了这行，Worker 写回的文件进不了仓库，构建期也读不到。
- 社区替换 `tags` 是**整组替换**，会让「同类地图」推荐发生变化（共同标签变少）。
  这是预期行为，但审核时要意识到这个连带影响。

### 攒批写回（2026-10-05）

第 8 节「审完不要立刻构建」那条建议**已落地**，审核动线因此变了两步：

```
/admin 点「通过」 ──▶ status=approved（进「待写回」队列，仓库还没动）
/admin 点「写回仓库」 ──▶ 一次 commit 写完这一批 ──▶ Cloudflare 重建 ──▶ 上线
```

- **为什么**：以前每通过一条就一次 commit + 一次构建。Cloudflare 免费版每月 3,000 构建分钟、
  同时只允许 1 个构建，逐条写回等于拿构建次数换即时性；攒一批只构建一次，也少一堆「只改一个字段」的提交。
- **实现**：`worker/community.ts` 新增 `commitFiles()`（Git Data API：blob → tree → commit → PATCH ref）。
  多个投稿 / 多张地图 / 连封面图片和删除一起，**一个 commit 装完**（多文件逐个 `PUT /contents` 做不到这点）。
  ref 冲突（有人同时推了 main）时那个 commit 成为孤儿，代码重放一次并前移分支，最多重试 3 次。
- **⚠️ 行为变化**：审核台点「通过」**不再等于发布** —— 不点「写回仓库」，内容不会出现在网站上。
  审核台顶部有「待写回 N 条」的提示条，就是这个原因。改主意可以「撤回」回待审。
- 已通过但还没写回的投稿，在 D1 里是 `approved`（`migrations/0002_submissions.sql` 里记了四个状态的语义）。
